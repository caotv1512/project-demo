Những phần đã đo được trên VPS giả lập sẽ được đánh dấu ✅; phần còn lại dựa trên tài liệu chính thức của AWS và **bạn nên làm thử một lượt trước khi đứng lớp**.

# A · BA KHÁC BIỆT LỚN SO VỚI VPS GIẢ LẬP

## A1. Lệnh đổi như thế nào

| Việc | VPS giả lập | **Máy chủ AWS thật** |
|---|---|---|
| Đăng nhập lần đầu | `ssh -p 2222 root@localhost` | `ssh -i quickbite.pem ubuntu@13.210.134.235` |
| Tài khoản đầu tiên | `root` + mật khẩu | **`ubuntu`** + file khoá `.pem` — **không có mật khẩu root** |
| Đăng nhập sau khi tạo deployer | `ssh -i ~/.ssh/... -p 2222 deployer@localhost` | `ssh -i ~/.ssh/... deployer@13.210.134.235` |
| Cổng SSH | 2222 | **22** (mặc định, không cần ghi) |
| Nạp lại SSH | `kill -HUP 1` | **`sudo systemctl reload ssh`** |
| Khi mất SSH | `docker exec -it vps-gia-lap bash` | **EC2 Instance Connect** hoặc **Session Manager** (mục H) |
| Tường lửa | Chỉ UFW | **Security Group + UFW** — hai lớp (mục C) |
| Cài Docker | Chạy được tới `apt install` | **Chạy được hết**, daemon bật bình thường |

## A2. Trên AWS có **hai** tường lửa, không phải một

Đây là nguyên nhân số một khiến người mới dùng AWS loay hoay hàng giờ.

```
Internet
   │
   ▼
┌──────────────────────────────┐
│  SECURITY GROUP              │  ← tường lửa của AWS, nằm NGOÀI máy chủ
│  (cấu hình trên AWS Console) │     Mặc định CHẶN HẾT chiều vào
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│  UFW                         │  ← tường lửa trong hệ điều hành
│  (cấu hình bằng SSH)         │     Thứ ta học ở BÀI 3
└──────────────┬───────────────┘
               ▼
          Ứng dụng
```

> ⚠️ **Gói tin phải qua được CẢ HAI mới tới ứng dụng.** Mở cổng ở UFW mà quên Security Group thì vẫn không ai gọi được — và ngược lại. Khi "mở cổng rồi mà vẫn không vào được", hãy kiểm tra lớp bạn **quên**, đừng mở thêm ở lớp đã mở.

## A3. IAM user **không phải** tài khoản Linux

Hai khái niệm này tên giống nhau nhưng hoàn toàn khác nhau. Nhầm chỗ này dẫn tới cấp quyền sai.

| | **IAM user** | **Linux user** (`deployer`) |
|---|---|---|
| Sống ở đâu | Trong **tài khoản AWS** | Trong **hệ điều hành của máy chủ** |
| Tạo bằng | AWS Console / CLI | `adduser` qua SSH |
| Cho phép làm gì | Bật/tắt máy, sửa Security Group, xem hoá đơn, tạo máy mới | Chạy lệnh **bên trong** máy chủ |
| Đăng nhập bằng | Mật khẩu AWS + MFA | **SSH key** |
| Xoá nó đi thì | Người đó không vào được AWS Console nữa, **nhưng vẫn SSH được** nếu còn khoá | Người đó không SSH được nữa, **nhưng vẫn vào AWS Console được** |

> 💡 **Một ví dụ cho dễ hình dung:** bạn thuê một căn phòng trong toà nhà.
> **IAM** là quyền với **ban quản lý toà nhà** — đổi phòng, xem hoá đơn, bật tắt điện tổng.
> **Linux user** là **chìa khoá phòng** — vào trong và kê dọn đồ đạc.
> Hai thứ hoàn toàn độc lập. Có chìa phòng không có nghĩa là nói chuyện được với ban quản lý.

# B · TẠO IAM USER TRÊN AWS

## B1. Vì sao không dùng tài khoản root của AWS

Tài khoản **root AWS** là email bạn dùng để đăng ký. Nó làm được **mọi thứ**, kể cả xoá toàn bộ tài khoản và thay đổi phương thức thanh toán. Không một chính sách nào giới hạn được nó.

> ⚠️ **Lộ tài khoản root AWS là mất toàn bộ hạ tầng và phát sinh hoá đơn không giới hạn.** Có những trường hợp thật mất hàng chục nghìn đô trong một đêm vì khoá root bị lộ trên GitHub và bị dùng để đào tiền số.

**Ba việc làm một lần rồi thôi với tài khoản root:**

| Việc | Vì sao |
|---|---|
| Bật **MFA** cho root | Lớp phòng thủ bắt buộc |
| **Xoá hết access key** của root (nếu có) | Root không bao giờ cần khoá API |
| Tạo một IAM user cho chính bạn, rồi **dùng nó hằng ngày** | Root chỉ để dành cho vài thao tác đặc biệt |

## B2. Tạo IAM user cho một người thật

**AWS Console → IAM → Users → Create user**

| Bước | Điền gì | Ghi chú |
|---|---|---|
| 1. User name | `caotv`, `sv-nguyenvana`… | **Một người một user**, không dùng chung |
| 2. Provide user access to the AWS Management Console | ✅ Tick nếu người đó cần bấm nút trên Console | Chỉ cần dùng CLI thì **không tick** |
| 3. Console password | Chọn **Autogenerated** | |
| 4. Users must create a new password at next sign-in | ✅ Tick | Bạn không biết mật khẩu của họ |
| 5. Permissions | **Add user to group** | Xem B3 — đừng gán policy trực tiếp |
| 6. Create user | | Lưu lại **URL đăng nhập** dạng `https://<ID-tài-khoản>.signin.aws.amazon.com/console` |

**Ngay sau khi tạo — bắt buộc bật MFA:**

**IAM → Users → chọn user → Security credentials → Multi-factor authentication (MFA) → Assign MFA device**

Chọn **Authenticator app** rồi quét QR bằng Google Authenticator / Microsoft Authenticator / 1Password.

> ⚠️ **Một IAM user có quyền sửa hạ tầng mà không có MFA là một mật khẩu đứng giữa kẻ tấn công và toàn bộ hệ thống của bạn.** Mật khẩu bị lộ qua lừa đảo là chuyện xảy ra hằng ngày; MFA chặn gần hết các trường hợp đó.

## B3. Gán quyền qua **Group**, không gán thẳng cho từng người

**IAM → User groups → Create group**

| Group | Gán policy | Dành cho |
|---|---|---|
| `quickbite-xem` | `AmazonEC2ReadOnlyAccess` | **Sinh viên** — chỉ nhìn, không sửa được gì |
| `quickbite-vanhanh` | Policy tự viết ở B4 | Người được phép bật/tắt máy |
| `quickbite-admin` | `AdministratorAccess` | **Chỉ bạn.** Không gán cho ai khác |

> 💡 **Vì sao qua Group?** Vì người thì thay đổi, còn vai trò thì không. Khi một sinh viên nghỉ, bạn xoá user — không phải đi dò xem họ từng được gán những policy nào. Khi cần đổi quyền cho cả lớp, bạn sửa **một** group thay vì ba mươi user.

## B4. Policy "đặc quyền tối thiểu" — chỉ thao tác được trên đúng máy của mình

Đây là policy nên dùng cho người vận hành. Nó cho phép **xem** mọi thứ, nhưng chỉ **bật/tắt** được những máy có gắn nhãn `Project = quickbite`.

**IAM → Policies → Create policy → JSON**, dán vào:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "XemDuocMoiTaiNguyenEC2",
      "Effect": "Allow",
      "Action": ["ec2:Describe*"],
      "Resource": "*"
    },
    {
      "Sid": "ChiBatTatMayCoTagProjectQuickbite",
      "Effect": "Allow",
      "Action": [
        "ec2:StartInstances",
        "ec2:StopInstances",
        "ec2:RebootInstances"
      ],
      "Resource": "arn:aws:ec2:ap-southeast-2:111122223333:instance/*",
      "Condition": {
        "StringEquals": { "aws:ResourceTag/Project": "quickbite" }
      }
    }
  ]
}
```

**Phải sửa hai chỗ:**

| Chỗ | Thay bằng |
|---|---|
| `ap-southeast-2` | Khu vực máy bạn. IP `13.210.x` thường là **ap-southeast-2 (Sydney)** — xác nhận ở góc trên bên phải Console |
| `111122223333` | **ID tài khoản AWS** của bạn (12 chữ số, bấm vào tên tài khoản góc trên bên phải) |

Rồi gắn nhãn cho máy chủ: **EC2 → Instances → chọn máy → Tags → Manage tags → Add tag**, với `Key = Project`, `Value = quickbite`.

> 💡 **Vì sao statement đầu để `"Resource": "*"`?** Vì các hành động `ec2:Describe*` **không hỗ trợ giới hạn theo tài nguyên** — AWS quy định như vậy. Bạn không thể viết "chỉ được xem máy này". Nhưng `Describe` chỉ **đọc**, nên để `*` là chấp nhận được. Mọi hành động **thay đổi** đều đã bị siết ở statement thứ hai.

> ⚠️ **Đừng gán `AmazonEC2FullAccess` cho sinh viên.** Nó cho phép **tạo máy mới**, và một máy GPU bị tạo nhầm rồi quên tắt có thể ngốn vài trăm đô một ngày vào hoá đơn của bạn.

## B5. Access key — chỉ tạo khi thật sự cần dùng CLI

Nếu người đó chỉ bấm nút trên Console thì **không cần access key**. Chỉ tạo khi họ phải chạy `aws` trên máy mình.

**IAM → Users → chọn user → Security credentials → Create access key → Command Line Interface (CLI)**

```bash
aws configure
```

Nhập Access Key ID, Secret Access Key, region `ap-southeast-2`, output `json`.

```bash
aws sts get-caller-identity
```

**Phải thấy:** ID tài khoản và ARN của user — xác nhận CLI đang dùng đúng danh tính.

> ⚠️ **Access key là mật khẩu vĩnh viễn ở dạng chữ.** Ba điều tuyệt đối:
> 1. **Không commit vào Git.** Bot quét GitHub tìm chuỗi `AKIA...` **trong vòng vài giây** sau khi push.
> 2. **Không dán vào Dockerfile, YAML, ảnh chụp màn hình hay slide.**
> 3. **Xoá ngay khi không còn dùng** — IAM → Security credentials → Delete.
>
> Nếu lỡ commit: **xoá key đó trên AWS ngay lập tức**, đừng chỉ xoá khỏi repo. Nó vẫn nằm trong lịch sử Git.

## B6. Khi đội đông hơn — IAM Identity Center

AWS hiện khuyến nghị dùng **IAM Identity Center** (tên cũ: AWS SSO) cho người dùng là **con người**, thay vì tạo IAM user cho từng người.

| | IAM user | **IAM Identity Center** |
|---|---|---|
| Thông tin đăng nhập | Cố định, lâu dài | **Tạm thời, tự hết hạn** |
| Nhiều tài khoản AWS | Mỗi tài khoản một user | **Một lần đăng nhập cho tất cả** |
| Khi người đó nghỉ việc | Phải nhớ xoá ở từng nơi | Tắt một chỗ là xong |
| Độ phức tạp khi dựng | Thấp | Cao hơn |

> 💡 **Với một lớp học thì IAM user là đủ và dễ hiểu hơn** — vì vậy tài liệu này dùng IAM user. Nhưng hãy nói cho sinh viên biết rằng ở công ty thật, cách làm chuẩn hiện nay là Identity Center. Biết tên nó để sau này không bỡ ngỡ.

# C · SECURITY GROUP — TƯỜNG LỬA THỨ HAI

**EC2 → Instances → chọn máy → Security → Security groups → Edit inbound rules**

| Type | Port | Source | Dùng cho |
|---|---|---|---|
| SSH | 22 | **My IP** | Quản trị — **không để `0.0.0.0/0`** |
| HTTP | 80 | `0.0.0.0/0` | Chuyển hướng sang HTTPS |
| HTTPS | 443 | `0.0.0.0/0` | Người dùng thật |

> ⚠️ **Chọn `My IP` cho SSH, đừng chọn `Anywhere`.** Khi đó dù khoá SSH có bị lộ, kẻ tấn công cũng không gọi tới được cổng 22 từ máy họ. Nhược điểm: đổi mạng (về nhà, ra quán cà phê) là phải cập nhật lại rule. Đổi lại, bạn loại bỏ được gần như toàn bộ lưu lượng dò quét.

**Những điều cần biết về Security Group:**

| Đặc điểm | Nghĩa là |
|---|---|
| Mặc định **chặn hết** chiều vào | Giống `ufw default deny incoming` |
| Mặc định **cho hết** chiều ra | `apt update`, `docker pull` chạy bình thường |
| **Có trạng thái** (stateful) | Cho phép chiều vào thì chiều trả lời tự động được phép — không cần mở thêm |
| Chỉ có luật **cho phép** | Không có khái niệm "chặn riêng một IP"; muốn chặn thì dùng Network ACL |
| Sửa là **có hiệu lực ngay** | Không cần khởi động lại máy |

> ⚠️ **Security Group KHÔNG thay thế UFW.** Nếu sau này bạn thêm máy chủ thứ hai trong cùng Security Group, chúng gọi được nhau mà Security Group không cản. UFW vẫn là lớp bảo vệ ở sát ứng dụng nhất. **Giữ cả hai.**

# D · KẾT NỐI LẦN ĐẦU VÀO EC2

## D1. Chuẩn bị file khoá `.pem`

Khi tạo máy EC2, AWS cho bạn tải về một file `.pem` — **chỉ tải được đúng một lần**. Mất là phải tạo khoá mới.

```bash
mv ~/Downloads/quickbite.pem ~/.ssh/
```
```bash
chmod 400 ~/.ssh/quickbite.pem
```

> ⚠️ ✅ **Bước `chmod 400` là bắt buộc, không phải làm cho đẹp.** Đây là lỗi đầu tiên gần như ai dùng AWS cũng gặp. Tôi đã thử với quyền `644`:
>
> ```
> @         WARNING: UNPROTECTED PRIVATE KEY FILE!          @
> Load key "quickbite.pem": bad permissions
> ubuntu@13.210.134.235: Permission denied (publickey).
> ```
>
> SSH **từ chối dùng** một khoá riêng mà người khác đọc được. Đổi sang `400` là vào được ngay.

## D2. Đăng nhập

```bash
ssh -i ~/.ssh/quickbite.pem ubuntu@13.210.134.235
```

**Phải thấy:** dấu nhắc đổi thành `ubuntu@ip-172-31-x-x:~$`

| Nếu dùng AMI | Tài khoản mặc định |
|---|---|
| Ubuntu | **`ubuntu`** |
| Amazon Linux | `ec2-user` |
| Debian | `admin` |

> 💡 **EC2 không có mật khẩu root.** Khác với VPS giả lập và khác với nhiều nhà cung cấp VPS khác. Tài khoản `ubuntu` đã có sẵn quyền `sudo` **không cần mật khẩu** — nên BÀI 1 trên máy thật, bạn gõ `sudo apt update` thay vì `apt update`.

# E · LÀM LẠI BÀI 1–4 TRÊN MÁY THẬT

Toàn bộ kiến thức giữ nguyên. Chỉ những chỗ sau thay đổi:

## BÀI 1 — thêm `sudo`

```bash
sudo apt update && sudo apt upgrade -y
```

> 🌐 Nếu `/var/run/reboot-required` xuất hiện: `sudo reboot`, đợi khoảng một phút rồi SSH vào lại. **Lần này máy thật sự khởi động lại**, khác hẳn sandbox.

## BÀI 2 — y nguyên, trừ lệnh reload

| Bước | Máy thật |
|---|---|
| Tạo user, cài khoá, `namei -l` | **Giống hệt** |
| Nạp lại SSH | `sudo systemctl reload ssh` (không phải `kill -HUP 1`) |
| Đăng nhập bằng deployer | `ssh -i ~/.ssh/quickbite_vps_ed25519 deployer@13.210.134.235` |

> ⚠️ **Nguyên tắc "thử trước, khoá sau" ở đây QUAN TRỌNG HƠN nhiều lần.** Trong sandbox, hỏng thì `docker exec` vào sửa. Trên máy thật, nếu bạn tắt `PasswordAuthentication` khi khoá chưa chạy **và** đã đóng phiên cũ, bạn phải dùng tới mục H — mất thời gian và có thể mất dịch vụ.
>
> **Giữ phiên `ubuntu@` ban đầu mở suốt** cho tới khi `deployer` + khoá đã được chứng minh là vào được.

## BÀI 3 — Docker chạy được hết, và nhớ Security Group

Phần cài Docker **chạy trọn vẹn** trên máy thật, kể cả hai lệnh mà sandbox không làm được:

```bash
sudo systemctl is-active docker
```
```bash
sudo docker run --rm hello-world
```

**Phải thấy:** `active`, rồi `Hello from Docker!`

> ⚠️ **Trước khi `sudo ufw enable`, kiểm tra Security Group đã cho phép cổng 22 chưa.** Nếu bạn khoá nhầm ở UFW **và** Security Group cũng chặn, bạn mất cả hai đường thông thường cùng lúc.

## BÀI 4 — đổi `.env` và chú ý RAM

```bash
nano .env
```

| Biến | Sandbox | **Máy thật** |
|---|---|---|
| `DB_PASSWORD` | `doi-mat-khau-nay-tren-vps-that` | **Mật khẩu mạnh, sinh ngẫu nhiên** |
| `APP_PORT` | `8081` | `8081` (vẫn bind `127.0.0.1`) |
| `IMAGE_REF` | `...:1.0.0` | **Tag cố định**, không dùng `latest` |

Sinh mật khẩu mạnh:

```bash
openssl rand -base64 24
```

> ⚠️ **Nếu máy chủ chỉ có 1 GB RAM**, ứng dụng Java (~300 MB) + PostgreSQL (~90 MB) + hệ điều hành là sát ngưỡng. Hãy tạo swap ở mục G2 **trước khi** chạy `up -d`, nếu không rất dễ gặp `Exit code 137`.

# F · ĐẶT BÍ DANH CHO MÁY CHỦ ✅

Gõ `ssh -i ~/.ssh/quickbite_vps_ed25519 deployer@13.210.134.235` ba chục lần một buổi là mỏi tay và dễ gõ nhầm. Đặt bí danh một lần:

```bash
nano ~/.ssh/config
```

Thêm vào:

```
Host quickbite
    HostName 13.210.134.235
    User deployer
    IdentityFile ~/.ssh/quickbite_vps_ed25519
    IdentitiesOnly yes
```

```bash
chmod 600 ~/.ssh/config
```

Từ giờ chỉ cần:

```bash
ssh quickbite
```

> ✅ **Đã kiểm chứng trên VPS giả lập:** bí danh hoạt động, và `scp` cũng dùng được luôn:
> ```
> scp .env quickbite:~/projects/quickbite-base/
> ```
>
> 💡 `IdentitiesOnly yes` bảo SSH **chỉ dùng đúng khoá bạn chỉ định**. Không có nó, SSH sẽ lần lượt đưa ra mọi khoá nó tìm thấy, và nếu bạn có nhiều khoá thì máy chủ có thể từ chối vì **thử quá số lần cho phép** — lỗi `Too many authentication failures` rất khó đoán.

# G · NHỮNG THỨ CHỈ MÁY THẬT MỚI CẦN

## G1. Elastic IP — giữ cho IP không đổi

Theo mặc định, IP công khai của EC2 **đổi mỗi khi bạn tắt rồi bật lại máy**. Nghĩa là `13.210.134.235` có thể thành một IP khác, và mọi thứ trỏ tới nó sẽ hỏng.

**EC2 → Elastic IPs → Allocate Elastic IP address → Associate** với máy của bạn.

> ⚠️ **AWS tính tiền Elastic IP khi nó KHÔNG được gắn vào máy nào đang chạy.** Cấp phát rồi để đó quên là mất tiền đều đặn. Dùng thì gắn, không dùng thì trả lại (Release).

## G2. Swap — phao cứu sinh cho máy chủ RAM nhỏ

EC2 **không có swap sẵn**. Máy 1 GB RAM chạy Java rất dễ bị OOM.

```bash
sudo fallocate -l 2G /swapfile
```
```bash
sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
```
```bash
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```
```bash
free -h
```

**Phải thấy:** dòng `Swap:` có dung lượng 2 GB thay vì `0B`.

> 💡 **Swap không làm máy nhanh hơn** — nó chậm hơn RAM rất nhiều. Nó chỉ làm **máy không chết** khi vượt ngưỡng trong chốc lát. Nếu ứng dụng dùng swap liên tục thì vấn đề thật là **máy quá nhỏ**, hãy nâng cấp chứ đừng tăng swap.

## G3. Tự động vá lỗi bảo mật

```bash
sudo apt install -y unattended-upgrades
```
```bash
sudo dpkg-reconfigure --priority=low unattended-upgrades
```

Máy chủ sẽ tự cài các bản vá bảo mật mà không cần bạn nhớ.

## G4. fail2ban — tự chặn IP dò mật khẩu

```bash
sudo apt install -y fail2ban
```
```bash
sudo systemctl enable --now fail2ban
```
```bash
sudo fail2ban-client status sshd
```

> 💡 **Đã tắt mật khẩu rồi thì fail2ban còn tác dụng gì?** Nó không còn để chặn đoán mật khẩu nữa, mà để **giảm nhiễu và giảm tải**: các bot vẫn gõ cửa hàng nghìn lần mỗi ngày, làm log phình ra và tốn tài nguyên. fail2ban chặn chúng ở mức mạng. Hãy mở log sau một ngày để sinh viên thấy con số thật — đó là minh hoạ thuyết phục nhất cho cả BÀI 2.

```bash
sudo journalctl -u ssh --since "24 hours ago" | grep -c "Invalid user"
```

## G5. Múi giờ và sao lưu

```bash
sudo timedatectl set-timezone Asia/Ho_Chi_Minh
```

**Sao lưu — thứ dễ quên nhất:** dữ liệu trong `quickbite-prod-data` giờ là **dữ liệu thật**.

**EC2 → Elastic Block Store → Lifecycle Manager** để tạo snapshot tự động hằng ngày.

> ⚠️ **Snapshot chưa từng được phục hồi thử thì không phải bản sao lưu — nó chỉ là một niềm tin.** Hãy thử phục hồi một lần, ngay khi mọi thứ còn bình thường.

# H · KHI MẤT SSH — BA ĐƯỜNG CỨU HỘ CỦA AWS

Trong sandbox ta dùng `docker exec`. Trên AWS có ba lựa chọn, theo thứ tự nên thử:

| # | Cách | Khi nào dùng được | Chuẩn bị trước |
|---|---|---|---|
| 1 | **EC2 Instance Connect** | Security Group cho phép cổng 22, máy còn chạy | Không cần gì |
| 2 | **Session Manager (SSM)** | **Không cần cổng 22 nào cả** | Phải gắn IAM role + cài SSM Agent **trước** |
| 3 | Gỡ ổ đĩa gắn sang máy khác | Mọi cách trên đều hỏng | Tốn thời gian, phải tắt máy |

**Cách 1 — EC2 Instance Connect:** EC2 → Instances → chọn máy → **Connect** → tab **EC2 Instance Connect** → Connect. Mở ngay một cửa sổ dòng lệnh trong trình duyệt.

> ⚠️ **Cách 1 vẫn đi qua cổng 22.** Nếu bạn tự khoá mình bằng cách chặn cổng 22 ở **Security Group**, nó cũng không vào được. Khi đó chỉ còn Session Manager — mà Session Manager **phải được chuẩn bị từ trước**.

**Chuẩn bị Session Manager ngay hôm nay, lúc còn bình thường:**

1. **IAM → Roles → Create role** → AWS service → EC2 → gắn policy `AmazonSSMManagedInstanceCore`
2. **EC2 → chọn máy → Actions → Security → Modify IAM role** → chọn role vừa tạo
3. Ubuntu 24.04 trên AWS đã có sẵn SSM Agent

Thử ngay:

```bash
aws ssm start-session --target i-0abc123def456
```

> ⚠️ **Đây là lời khuyên quan trọng nhất của cả file này.** Hãy mở thử **cả hai** đường cứu hộ **ngay hôm nay**, lúc mọi thứ đang chạy tốt. Tìm hiểu chúng lần đầu trong lúc đang mất kết nối, giữa đêm, với dịch vụ đang ngừng — là trải nghiệm không ai muốn có.

# J · BẢNG LỖI RIÊNG CỦA MÁY CHỦ AWS

| Triệu chứng | Nguyên nhân thường gặp | Sửa |
|---|---|---|
| `WARNING: UNPROTECTED PRIVATE KEY FILE!` | File `.pem` quyền quá rộng | `chmod 400 ~/.ssh/quickbite.pem` ✅ |
| `Permission denied (publickey)` ngay lần đầu | Sai tên tài khoản | Ubuntu dùng `ubuntu@`, không phải `root@` hay `ec2-user@` |
| SSH **treo rồi timeout** | **Security Group** chưa mở cổng 22 từ IP của bạn | Sửa inbound rule, chọn **My IP** |
| Hôm qua vào được, hôm nay timeout | **IP mạng của bạn đã đổi** (đổi wifi, đổi nhà mạng) | Cập nhật lại **My IP** trong Security Group |
| `Too many authentication failures` | SSH đưa ra quá nhiều khoá | Thêm `IdentitiesOnly yes` vào `~/.ssh/config` |
| IP đổi sau khi bật lại máy | Chưa cấp Elastic IP | Mục G1 |
| Mở cổng ở UFW rồi vẫn không gọi được | **Quên lớp Security Group** | Mở ở cả hai nơi |
| Mở Security Group rồi vẫn không gọi được | **Quên lớp UFW** | `sudo ufw status` rồi mở |
| `Exit code 137` | Hết RAM | Tạo swap (G2), hoặc nâng cấp máy |
| Hoá đơn cao bất thường | Elastic IP không dùng, hoặc máy bị tạo nhầm | Kiểm tra **Billing → Cost Explorer** |
| `UnauthorizedOperation` khi gọi `aws` | IAM user thiếu quyền | Kiểm tra policy của group |
| `REMOTE HOST IDENTIFICATION HAS CHANGED` | Tạo lại máy nên vân tay đổi | `ssh-keygen -R 13.210.134.235` ✅ |
