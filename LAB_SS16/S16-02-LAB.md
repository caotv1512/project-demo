# PHẦN 1 — XÁC ĐỊNH SERVICE VÀ ĐỌC LOG

## 1.1 · Vào đúng thư mục chứa `docker-compose.yml`

**Lệnh**

```bash
cd ~/Downloads/quickbite-demo/session-05/stack
```

**Lệnh** — xác nhận đang đứng đúng chỗ

```bash
ls docker-compose.yml
```

**Ví dụ**

```
docker-compose.yml
```

**Giải thích**

`docker compose logs` chỉ chạy được khi terminal đang đứng trong thư mục có `docker-compose.yml`. Đứng sai chỗ sẽ báo `no configuration file provided`.

Mọi lệnh từ đây đến hết PHẦN 5 đều chạy trong thư mục này.

## 1.2 · Liệt kê service name

**Lệnh**

```bash
docker compose config --services
```

**Ví dụ**

```
order-service
restaurant-service
user-service
api-gateway
notification-service
```

**Giải thích**

Đây là **service name** — tên dùng cho mọi lệnh `docker compose`. Thứ tự in ra **không theo thứ tự chữ cái**, cũng không theo thứ tự trong file Compose, nên đừng dựa vào vị trí dòng để đoán tên. Lệnh này đọc trực tiếp từ file Compose, nên kết quả luôn đúng, không phải đoán.

## 1.3 · Đối chiếu service name với container name

**Lệnh**

```bash
docker compose ps --format '{{.Service}}\t{{.Name}}\t{{.Status}}'
```

**Ví dụ**

```
api-gateway	quickbite5-gateway	Up 4 days
notification-service	quickbite5-notification	Up 4 days
order-service	quickbite5-order	Up 4 days
restaurant-service	quickbite5-restaurant	Up 4 days
user-service	quickbite5-user	Up 4 days
```

**Giải thích**

Hai cột đầu là hai hệ tên khác nhau, dùng cho hai nhóm lệnh khác nhau:

| Cột | Loại tên | Dùng với |
|---|---|---|
| `{{.Service}}` | Service name | `docker compose logs`, `docker compose stop` |
| `{{.Name}}` | Container name | `docker logs`, `docker exec` |

> ⚠️ Dùng `docker compose logs quickbite5-order` sẽ báo `no such service: quickbite5-order`. Đó là container name, không phải service name.

## 1.4 · Xem N dòng log gần nhất

**Cấu trúc câu lệnh**

```
docker compose logs --tail <SO_DONG> <SERVICE_NAME>
```

**Lệnh**

```bash
docker compose logs --tail 10 order-service
```

**Ví dụ**

```
quickbite5-order  | 2026-11-02T06:48:06.826Z  INFO 1 --- [order-service] [nio-8083-exec-5] com.quickbite.order.OrderController      : [BUOC 2] Tao don #4 PENDING - Pho Thin / Pho bo tai lan / 75000d
quickbite5-order  | 2026-11-02T06:48:07.079Z  INFO 1 --- [order-service] [nio-8083-exec-5] com.quickbite.order.OrderController      : [BUOC 3] Da tru 75000d cua user #1
```

**Giải thích**

| Thành phần | Vai trò |
|---|---|
| `--tail 10` | Chỉ lấy 10 dòng cuối. Không có tham số này thì Docker in **toàn bộ** lịch sử log |
| `quickbite5-order  \|` | Tiền tố do Compose thêm vào để biết dòng log thuộc container nào |

## 1.5 · Xem log kèm mốc thời gian và lọc theo khoảng

**Cấu trúc câu lệnh**

```
docker compose logs -t --since <KHOANG_THOI_GIAN> <SERVICE_NAME>
```

**Lệnh**

```bash
docker compose logs -t --since 30m order-service
```

**Giải thích**

| Tham số | Ý nghĩa |
|---|---|
| `-t` | Thêm mốc thời gian **của Docker** vào đầu mỗi dòng |
| `--since 30m` | Chỉ lấy log trong 30 phút gần nhất |

Đơn vị của `--since`: `s` giây, `m` phút, `h` giờ. Cũng nhận mốc tuyệt đối, ví dụ `--since 2026-11-02T06:45:00`.

Sau khi thêm `-t`, mỗi dòng có **hai** mốc thời gian:

```
2026-11-02T06:48:06.826925722Z 2026-11-02T06:48:06.826Z  INFO 1 --- [order-service] ...
└─ mốc Docker ghi nhận ──────┘ └─ mốc ứng dụng tự ghi ─┘
```

Mốc đầu do Docker thêm, mốc sau do Logback của ứng dụng in ra. Hai mốc lệch nhau vài phần nghìn giây là bình thường.

## 1.6 · Theo dõi log theo thời gian thực

**Lệnh**

```bash
docker compose logs -f --tail 5 order-service
```

**Giải thích**

`-f` (follow) giữ terminal mở và in dòng mới ngay khi phát sinh. Thêm `--tail 5` để không phải cuộn qua toàn bộ lịch sử trước khi theo dõi.

**Lệnh** — thoát khỏi chế độ theo dõi

```
Ctrl + C
```

> ⚠️ `Ctrl + C` chỉ dừng việc **xem** log. Container vẫn chạy bình thường. Kiểm chứng bằng lệnh dưới.

**Lệnh** — xác nhận container vẫn sống sau khi nhấn `Ctrl + C`

```bash
docker compose ps --format '{{.Service}}\t{{.Status}}' order-service
```

**Ví dụ**

```
order-service	Up 4 days
```


```
quickbite5-order  | 2026-11-02T06:48:07.079Z  INFO 1 --- [order-service] [nio-8083-exec-5] com.quickbite.order.OrderController      : [BUOC 3] Da tru 75000d cua user #1
quickbite5-order  | 2026-11-02T06:48:07.088Z  INFO 1 --- [order-service] [nio-8083-exec-5] com.quickbite.order.OrderController      : [BUOC 4] Nha hang Pho Thin da nhan don #4
```

Đó là lý do phải có quy ước ghi log cho **mọi** service, không chỉ service chính.

## 1.8 · Lưu log ra file để phân tích

**Lệnh**

```bash
docker compose logs -t --since 1h order-service > /tmp/order-1h.log
```

**Lệnh** — kiểm tra file vừa ghi

```bash
wc -l /tmp/order-1h.log && head -2 /tmp/order-1h.log
```

**Ví dụ**

```
      31 /tmp/order-1h.log
quickbite5-order  | 2026-11-02T11:35:26.696832250Z 
quickbite5-order  | 2026-11-02T11:35:26.696860625Z   .   ____          _            __ _ _
```

Số dòng khác nhau tuỳ máy. Hai dòng đầu ở ví dụ này là logo khởi động của Spring Boot vì container vừa được dựng lại trong vòng một giờ.

> 💡 `--since 1h` chỉ lấy log của một giờ gần nhất. Container đã chạy lâu hơn một giờ thì phần khởi động nằm ngoài cửa sổ thời gian: file chỉ còn log nghiệp vụ và hai dòng đầu sẽ là `[BUOC ...]`.

**Giải thích**

Ghi log ra file cho phép dùng `grep`, `awk`, `sort` nhiều lần trên cùng một tập dữ liệu mà không phải gọi lại Docker. Khi điều tra sự cố, đây là bước đầu tiên trước khi phân tích.

# PHẦN 2 — ĐỌC CẤU TRÚC DÒNG LOG VÀ LỌC THEO LEVEL

## 2.1 · Tách bảy phần của một dòng log

**Lệnh** — lấy một dòng log nghiệp vụ

```bash
docker compose logs --tail 200 order-service | grep 'BUOC 2' | tail -1
```

**Ví dụ**

```
quickbite5-order  | 2026-11-02T06:48:06.826Z  INFO 1 --- [order-service] [nio-8083-exec-5] com.quickbite.order.OrderController      : [BUOC 2] Tao don #4 PENDING - Pho Thin / Pho bo tai lan / 75000d
```

**Giải thích**

| Phần | Giá trị | Ý nghĩa |
|---|---|---|
| Tiền tố Compose | `quickbite5-order  \|` | Container nào in dòng này |
| Thời điểm | `2026-11-02T06:48:06.826Z` | Múi giờ UTC — dùng để khớp log giữa các service |
| Level | `INFO` | Mức log |
| PID | `1` | Process ID trong container; trong Docker hầu như luôn là `1` |
| Tên ứng dụng | `[order-service]` | Lấy từ `spring.application.name` |
| Thread | `[nio-8083-exec-5]` | Luồng xử lý — cùng thread nghĩa là cùng một request |
| Logger | `com.quickbite.order.OrderController` | Class đã ghi dòng log |
| Nội dung | `[BUOC 2] Tao don #4 ...` | Thông điệp do lập trình viên viết |

## 2.2 · Truy vết một request bằng tên thread

**Lệnh** — tìm tên thread của đơn hàng gần nhất

```bash
TH=$(docker compose logs --tail 200 order-service | grep 'BUOC 2' | tail -1 | sed 's/.*\[\(nio-[^]]*\)\].*/\1/')
echo "Thread: $TH"
```

**Ví dụ**

```
Thread: nio-8083-exec-5
```

**Lệnh** — lấy toàn bộ dòng log của đúng request đó

```bash
docker compose logs --tail 300 order-service | grep "\[$TH\]" | sed 's/^quickbite5-order  | //'
```

**Ví dụ**

```
2026-11-02T06:48:06.826Z  INFO 1 --- [order-service] [nio-8083-exec-5] com.quickbite.order.OrderController      : [BUOC 2] Tao don #4 PENDING - Pho Thin / Pho bo tai lan / 75000d
2026-11-02T06:48:07.079Z  INFO 1 --- [order-service] [nio-8083-exec-5] com.quickbite.order.OrderController      : [BUOC 3] Da tru 75000d cua user #1
2026-11-02T06:48:07.088Z  INFO 1 --- [order-service] [nio-8083-exec-5] com.quickbite.order.OrderController      : [BUOC 4] Nha hang Pho Thin da nhan don #4
2026-11-02T06:48:07.796Z  INFO 1 --- [order-service] [nio-8083-exec-5] com.quickbite.order.OrderController      : [BUOC 5-6] Don #4 CONFIRMED, da gui thong bao
```

**Giải thích**

Tên thread là cách truy vết **thủ công** trong phạm vi một service. Hạn chế của nó:

| Hạn chế | Hậu quả |
|---|---|
| Thread được tái sử dụng cho request khác | Hai request cách nhau vài giây có thể cùng tên thread |
| Mỗi service có bộ tên thread riêng | Không nối được chuỗi `order-service` → `user-service` |

## 2.3 · Lọc và đếm log theo level

**Lệnh** — đếm số dòng theo từng level

```bash
for L in ERROR WARN INFO DEBUG TRACE; do
  printf "%-6s %s\n" "$L" "$(docker compose logs order-service 2>/dev/null | grep -c " $L ")"
done
```

**Ví dụ**

```
ERROR  0
WARN   0
INFO   29
DEBUG  0
TRACE  0
```

> 💡 Con số phụ thuộc vào lịch sử của container. Vừa dựng lại container thì `WARN` và `ERROR` đều bằng `0` — PHẦN 4 sẽ tạo ra chúng.

**Lệnh** — chỉ đọc các dòng bất thường

```bash
docker compose logs order-service | grep -E ' (WARN|ERROR) ' | sed 's/^quickbite5-order  | //' | cut -c1-150
```

**Ví dụ**

```
2026-11-02T06:47:51.583Z  WARN 1 --- [order-service] [nio-8083-exec-1] .w.s.m.s.DefaultHandlerExceptionResolver : Resolved [org.springframework.web
2026-11-02T06:48:40.632Z  WARN 1 --- [order-service] [nio-8083-exec-8] com.quickbite.order.OrderController      : [BUOC 3] THAT BAI - huy don #5
```

Không in gì nghĩa là chưa có dòng `WARN` hay `ERROR` nào. Đó là trạng thái bình thường của một container vừa dựng lại.

**Giải thích**

`DEBUG` và `TRACE` đều bằng `0` vì `order-service` đang ở ngưỡng `INFO` — đúng cấu hình Production. PHẦN 3 sẽ đổi ngưỡng này.

# PHẦN 3 — ĐỔI LOG LEVEL TẠM THỜI KHI ĐIỀU TRA

## 3.1 · Tạo file đổi log level

**Lệnh** — về thư mục của buổi 16

```bash
cd ~/Downloads/quickbite-demo/LAB_SS16
```

**Lệnh** — mở trình soạn thảo

```bash
nano log-debug.yml
```

**Cấu trúc file** — gõ nội dung sau, rồi lưu bằng `Ctrl+O` → `Enter` → `Ctrl+X`

```yaml
# File chong len docker-compose.yml cua session-05, chi doi log level.
# Khong sua gi trong session-05.
services:
  order-service:
    environment:
      - LOGGING_LEVEL_COM_QUICKBITE_ORDER=DEBUG
      - LOGGING_LEVEL_ORG_SPRINGFRAMEWORK_WEB=DEBUG
```

**Giải thích**

| Thành phần | Vai trò |
|---|---|
| `services: order-service:` | Chỉ tác động lên một service; bốn service còn lại giữ nguyên `INFO` |
| `LOGGING_LEVEL_COM_QUICKBITE_ORDER` | Biến môi trường tương đương `logging.level.com.quickbite.order` trong `application.yml` |
| `LOGGING_LEVEL_ORG_SPRINGFRAMEWORK_WEB` | Bật `DEBUG` cho tầng web của Spring, để thấy chi tiết request |

Spring Boot đổi dấu `.` thành `_` và viết hoa toàn bộ khi đọc cấu hình từ biến môi trường. Nhờ vậy đổi được log level **không cần sửa code và không cần build lại**.

**Lệnh** — kiểm tra nội dung file

```bash
cat log-debug.yml
```

> 💡 Thư mục `LAB_SS16/` đã có sẵn một bản `log-debug.yml` mẫu. Nếu `cat` ra đúng nội dung trên mà bạn chưa gõ gì, đó là bản mẫu — vẫn dùng được, nhưng nên tự gõ lại một lần để hiểu từng dòng.

**Lệnh** — kiểm tra cú pháp YAML hợp lệ khi ghép với file Compose của `session-05`

```bash
cd ~/Downloads/quickbite-demo/session-05/stack && docker compose -f docker-compose.yml -f ../../LAB_SS16/log-debug.yml config --quiet && echo "Cu phap hop le"
```

**Ví dụ**

```
Cu phap hop le
```

|---|---|
| `Recreated` | Container bị **xoá và tạo lại**. Biến môi trường chỉ đọc được lúc container khởi động, không đổi được khi đang chạy |
| Chỉ một container | Bốn service còn lại không bị khởi động lại, hệ thống vẫn phục vụ bình thường |

> ⚠️ Dựng lại container làm mất log cũ của container đó. Nếu cần giữ log để điều tra, lưu ra file trước — mục 1.8.

**Lệnh** — khởi động lại `api-gateway` sau khi dựng lại `order-service`

```bash
docker compose restart api-gateway && sleep 25
```

**Giải thích**

Dựng lại container **có thể làm đổi địa chỉ IP** của nó trong mạng Docker. `api-gateway` giữ sẵn một connection pool trỏ tới IP cũ, nên request đi qua gateway sẽ trả `HTTP 500` kèm `Connection refused` — dù `order-service` hoàn toàn khoẻ.

Lỗi này **không xảy ra mọi lần**: nếu Docker cấp lại đúng IP cũ thì không có gì hỏng. Vì vậy trong cùng một lớp sẽ có người gặp, người không. Lệnh khởi động lại gateway ở trên vô hại trong cả hai trường hợp, nên cứ chạy để khỏi phải đoán.

**Lệnh** — xác nhận đã đặt được đơn

```bash
curl -s -X POST "http://localhost:8000/api/v1/orders?userId=1&restaurantId=1"
```

**Ví dụ**

```
{"message":"Dat hang thanh cong","refunded":false,"orderId":25,"status":"CONFIRMED"}
```

## 3.3 · Đo lượng log mà DEBUG sinh ra

**Lệnh** — đếm số dòng log trước và sau một request

```bash
B=$(docker compose logs order-service | wc -l)
```


**Giải thích**

Con số này là căn cứ định lượng cho quy tắc *Production giữ ngưỡng `INFO`*. Mục 3.4 sẽ đo lại ở ngưỡng `INFO` để so sánh.

**Lệnh** — xác nhận không còn dòng `DEBUG`

**Lệnh** — khởi động lại gateway lần nữa, vì `order-service` vừa được dựng lại

## 4.2 · Bước 1 — kiểm tra trạng thái container

**Lệnh**

```bash

```

**Ví dụ**


**Giải thích**

| Thành phần | Ý nghĩa |
|---|---|
| `-a` | Hiện **cả** container đã dừng. Không có `-a` thì `user-service` biến mất khỏi danh sách |
| `Exited (143)` | Mã 143 = `128 + 15` = bị dừng bằng tín hiệu `SIGTERM`, tức có người chủ động dừng |
| `Exited (137)` | Mã 137 = `128 + 9` = bị `SIGKILL`, thường do hết RAM (OOM) |
| `Restarting` | Container sập rồi được Docker khởi động lại liên tục — dấu hiệu lỗi nghiêm trọng |

> ⚠️ Luôn bắt đầu từ bước này, không bắt đầu từ việc đọc log. Container đã chết thì log của nó dừng từ lúc chết, đọc mãi cũng không thấy nguyên nhân sự cố vừa xảy ra.

**Lệnh** — lọc log của service chính trong 5 phút gần nhất

## 4.4 · Bước 4 — truy vết luồng service

**Lệnh** — đọc log nghiệp vụ của đơn hàng vừa thất bại


**Ví dụ**

```
2026-11-02T06:48:40.632Z  WARN 1 --- [order-service] [nio-8083-exec-8] com.quickbite.order.OrderController      : [BUOC 3] THAT BAI - huy don #5
```

**Giải thích**

Đọc hai dòng này là định vị được vị trí lỗi:

| Quan sát | Kết luận |
|---|---|
| `BUOC 2` thành công, `BUOC 3` thất bại | Lỗi nằm ở bước trừ tiền, không phải ở bước tạo đơn |

| Level là `WARN` chứ không phải `ERROR` | Ứng dụng đã xử lý được: huỷ đơn và hoàn tiền |

**Lệnh** — kiểm chứng service bị nghi là nguyên nhân

```bash

```

**Ví dụ**

```

quickbite5-user  | 2026-11-02T07:02:27.638Z  INFO 1 --- [user-service] [ionShutdownHook] com.zaxxer.hikari.HikariDataSource : HikariPool-1 - Shutdown initiated...
quickbite5-user  | 2026-11-02T07:02:27.656Z  INFO 1 --- [user-service] [ionShutdownHook] com.zaxxer.hikari.HikariDataSource : HikariPool-1 - Shutdown completed.
```

**Giải thích**

Đây là bằng chứng kết thúc cuộc điều tra:

| Quan sát | Kết luận |
|---|---|
| Dòng cuối là `Shutdown completed` lúc `07:02:27` | `user-service` đã tắt, và tắt **có trình tự** — không phải sập đột ngột |

Đối chiếu với `Exited (143)` ở mục 4.2: hai bằng chứng độc lập cùng chỉ ra service bị dừng chủ động, không phải sập vì lỗi.

**Cấu trúc câu lệnh** — dạng an toàn

**Giải thích**

| Mã lỗi / `reason` đã chuẩn hoá | JWT access token, refresh token |
| Thời gian xử lý request | API key, secret key |

## 6.6 · Đặt đơn trả về `HTTP 500` dù mọi container đều `Up`


```
failed: Connection refused
```

Địa chỉ IP thay đổi theo từng máy và từng lần dựng container.

**Ví dụ** — không in ra gì

Lệnh không in dòng nào là kết quả bình thường, kể cả ngay sau khi vừa dựng lại `order-service`. Gateway chỉ ghi dòng lỗi khi có request thật đi qua nó. Muốn kiểm chứng thì đặt một đơn rồi chạy lại lệnh trên.

**Giải thích**

Thông báo lỗi nêu rõ **địa chỉ IP** mà gateway đang cố gọi. Đó là đầu mối duy nhất cần thiết.

**Lệnh** — so IP trong lỗi với IP thật hiện tại của `order-service`



**Giải thích**

| Kết quả | Nghĩa | Xử lý |
|---|---|---|
| IP trong log **khác** IP hiện tại | Gateway giữ connection pool trỏ tới container đã bị xoá | Khởi động lại gateway, lệnh dưới |
| IP trong log **trùng** IP hiện tại | Nguyên nhân khác — `order-service` chưa khởi động xong | Đợi rồi kiểm lại bằng `docker compose logs --tail 5 order-service` |

Dựng lại container làm Docker cấp IP mới cho nó. Gateway không tra DNS lại cho những kết nối đã mở sẵn trong pool, nên vẫn gọi vào IP của container đã chết.
